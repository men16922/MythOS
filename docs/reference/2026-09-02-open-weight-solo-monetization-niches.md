# Open-Weight FM 기반 1인 수익화 — 니치 20개 평가

작성 2026-09-02 · 성격: 레퍼런스(의사결정 근거). 실행 항목이 아니라 **판단의 재료**입니다.
선행 문서: `docs/reference/2026-08-30-self-hosted-inference-and-mythos-as-research-platform.md` (이하 **08-30 문서**).

기획서의 최종 질문에 답합니다.

> Open-Weight FM의 확산으로 1인 개발자가 Big Tech가 진입하지 않는 Long-tail AI 시장을 어떻게 발견하고, 특화하고, 수익화할 수 있는가?

**결론 먼저.** 기획서의 밸류체인은 기술적으로 성립합니다 — multi-LoRA 서빙은 실제로 어댑터당 수 MB로 수백 테넌트를 한 GPU에 올립니다. 그런데 **이 사업 모델의 병목은 GPU 비용이 아닙니다.** 인프라 손익분기는 놀랄 만큼 낮고(§2), 진짜 벽은 두 개입니다: **(1) distribution — GPU를 채울 만큼의 고객을 어떻게 얻는가, (2) 품질 증명 — 내 LoRA가 API보다 낫다는 것을 어떻게 *측정*하는가.** 두 번째는 이 리포지토리가 이미 값비싸게 배운 문제이고(judge 노이즈 바닥 ~1점), **그게 이 기획에서 우리가 남들보다 앞서 있는 유일한 지점**입니다.

## 1. 기획서의 밸류체인에서 실제로 검증한 고리

기획서는 다섯 단계를 제시합니다. 각 고리가 실제로 버티는지 따로 봅니다.

| 고리 | 상태 | 근거 |
|---|---|---|
| Frontier FM → Open-Weight FM | ✅ 성립 | Qwen3부터 알리바바 오픈웨이트 전량 **Apache 2.0**. DeepSeek 계열도 상용 친화. Llama만 **MAU 7억 임계**가 붙지만 1인 개발자에게는 사실상 무제한 |
| 개인 Customization (LoRA/RAG) | ✅ 성립 | 진입 비용이 가장 많이 내려간 구간 |
| **Shared GPU Serving** | ✅ **기술적으로 성립 — 이게 기획서의 핵심 주장이고, 맞습니다** | vLLM/LoRAX/S-LoRA가 PagedAttention 위에서 어댑터 **핫로딩/축출을 ms 단위**로 지원. 어댑터는 base의 KV 캐시와 attention 레이어를 공유하고 **델타 가중치만 테넌트별**이라 테넌트당 VRAM 오버헤드가 MB 단위 |
| Vertical AI Product | ⚠️ 여기가 병목 | 기술이 아니라 distribution |
| Subscription / API / License | ⚠️ 니치마다 갈림 | §4의 수익모델 축 |

### 1-1. 그러나 multi-LoRA에도 실측된 함정이 있습니다

vLLM 초기 구현에서 **multi-LoRA의 TTFT가 base 모델 대비 10배**였던 사례가 보고돼 있습니다. 원인은 어댑터가 아니라 Triton 컴파일러가 입력 길이 의존 변수를 컴파일 타임 상수로 취급해 **컨텍스트 길이가 바뀔 때마다 `fused_moe_lora` 커널을 재컴파일**한 것입니다.

이건 08-30 문서 §2의 **규칙 6(계층은 공짜가 아니고, 저동시성에서 TTFT로 먼저 나타난다)** 의 또 다른 사례입니다. 그리고 지연 민감형 제품(스트리밍 서사, 실시간 챗)에서 TTFT는 곧 체감 품질입니다. **"어댑터는 MB밖에 안 든다"는 VRAM 이야기이지 지연 이야기가 아닙니다.**

→ 실행 함의: multi-LoRA를 사업 전제로 삼기 전에 **자기 워크로드의 컨텍스트 길이 분포에서 TTFT를 재야 합니다.** MythOS는 이걸 잴 수 있는 유일한 자산을 이미 갖고 있습니다 — `labs/wsl2-vllm-baseline/` 하네스 + 실제 시퀀스가 든 골든 뱅크(08-30 문서 §5-4).

## 2. 손익분기 — 08-30 문서가 비워 둔 계산

### 2-1. 좌변: API 총비용 (MythOS 루프 1회)

실측 워크로드 형태를 그대로 대입합니다.

| 항목 | 값 | 출처 |
|---|---|---|
| 호출당 입력 | 7,098 tok (중앙값) | 실측 |
| 호출당 출력 | 235 tok (중앙값) | 실측 |
| 루프당 호출 | ~50회 | 뱅크 실측(47~59 장면) |
| 프리픽스 공유율 | ~68% | 실측(3개 arm에서 안정) |
| Gemini 3.5 Flash | 입력 $0.75/M · 출력 $4.50/M · **캐시 입력 $0.075/M** | 2차 출처 |

```
입력 총량 = 7,098 × 50 = 354,900 tok
  캐시 미적중분 32% = 113,568 × $0.75/M = $0.0852
  캐시 적중분   68% = 241,332 × $0.075/M = $0.0181
출력 총량 = 15,000 tok × $4.50/M       = $0.0675
─────────────────────────────────────────────────
루프당 API 비용 ≈ $0.171   (캐시 적중 시)
                ≈ $0.334   (캐시 전무 시)
```

### ★ 여기서 나온 첫 번째 결과는 니치 평가가 아니라 우리 리포지토리에 대한 것입니다

리포 전역에 인용되는 **`cost_per_loop_usd` ~$1.0/loop 는 현재 단가 기준으로 약 6배 과대**입니다. 두 가지가 겹쳤습니다: (a) 원래부터 측정이 아니라 문서화된 추정치였고, (b) Flash 입력 단가가 최근 90일 만에 50% 내렸습니다.

이건 **자체 호스팅을 더 멀어지게 만드는 방향**입니다. 08-30 문서의 결론("지금은 API가 맞다")이 약해지는 게 아니라 **강해집니다.** 그리고 프리픽스 설계(§1-3 of 08-30)가 캐시 할인을 받는다면 좌변은 더 내려갑니다.

> ⚠️ 이 $0.171은 **여전히 측정이 아닙니다.** `usage.py`가 배포돼 `cached_tokens`가 실제로 찍혀야 확정됩니다. 지금은 "실측 토큰량 × 2차 출처 단가"입니다.

### 2-2. 우변: 자체 GPU 총비용

| 항목 | 값 | 출처 |
|---|---|---|
| A100 80GB | $0.67~1.07/hr (on-demand), $0.60/hr (spot) | 2차 출처 |
| H100 | $1.49~2.50/hr (저가 구간), 최대 $6.98/hr | 2차 출처 |
| RTX 4090 | $0.12~0.34/hr | 2차 출처 |

A100 80GB @ **$1.00/hr** 가정, 8B급 dense 모델(08-30 §3-3: 32B 미만은 dense).

**가정 — 이 문서에서 가장 약한 숫자입니다(§8):** prefill 10,000 tok/s, decode 1,000 tok/s (배칭 포화 시).

```
루프당 GPU 시간 = 354,900 / 10,000  (prefill) = 35.5s
                + 15,000 / 1,000    (decode)  = 15.0s
                                              ≈ 50.5 GPU-초
루프당 GPU 비용 = 50.5 / 3600 × $1.00 = $0.0140
```

### 2-3. 두 개의 손익분기

**(a) 인프라만 볼 때**

```
$0.0140 / $0.171 = 8.2%
```

→ **GPU가 하루 2시간만 실제로 일하면 인프라 비용은 자체 호스팅이 이깁니다.** 이 숫자는 직관보다 훨씬 낮습니다. 기획서의 "Shared GPU Serving"이 실제로 작동하는 이유입니다 — 여러 테넌트의 LoRA를 한 GPU에 얹는 목적이 정확히 이 **가동률(utilization)** 을 채우는 것이기 때문입니다.

**(b) 운영 시간을 넣을 때 — 이쪽이 진짜 임계입니다**

08-30 문서가 강조한 항목입니다: 자체 호스팅의 진짜 비용은 GPU가 아니라 **사람 시간**입니다(교재의 Baseten 77-구성 튜닝 사례, p119-121).

```
월 운영 10시간 × 기회비용 $50/hr = $500/월
루프당 절감액 = $0.171 − $0.014 = $0.157
손익분기 = $500 / $0.157 ≈ 3,185 루프/월 ≈ 106 루프/일
```

### 2-4. 그래서 결론이 08-30에서 바뀌는가 — 아니오, 그러나 이유가 바뀝니다

| | 08-30 문서 | 이 문서 |
|---|---|---|
| 결론 | 지금 자체 호스팅은 손해 | **동일** |
| 이유 | 규모 미달 (일 1억 토큰 · 100B+ 모델 · disaggregation 조건 p151) | **그 조건은 disaggregation의 조건이지 자체 서빙의 조건이 아니었음.** 단일 GPU 자체 서빙의 임계는 훨씬 낮음 |
| 임계 | 정성적("자릿수가 다르다") | **정량적: 가동률 8% / 106 루프/일** |
| 남는 블로커 | 품질 축 (judge ~1점 노이즈) | **동일 — 그리고 이게 유일하게 안 풀린 것** |

**정정할 것 하나.** 08-30 문서는 p151의 세 조건(일 1억~10억 토큰, 100B+, prefill-heavy)을 자체 호스팅 일반의 문턱처럼 인용했지만, 그 세 조건은 **disaggregation(PD 분리)의 도입 조건**입니다. 단일 GPU + vLLM + prefix caching 수준의 자체 서빙은 그보다 두 자릿수 낮은 규모에서 성립합니다. 결론은 같지만 근거는 이쪽이 정확합니다.

## 3. 평가 축의 조작적 정의

점수를 붙이기 전에 각 축이 무엇을 세는지 고정합니다. **정의 없는 1~5는 취향의 다른 이름입니다.**

| 축 | 방향 | 1점 | 5점 | 조작적 질문 |
|---|---|---|---|---|
| **시장성** | 높을수록 좋음 | 취미 수준, 지불 의사 불명 | 명확한 지불 의사 + 도달 경로 존재 | **1인이 12개월 내 월 $5k MRR 경로가 보이는가.** TAM이 아니라 *도달 가능한* 수요 |
| **기술난이도** | 낮을수록 좋음 | 프롬프트 + 기성 API | 다단 파이프라인 + custom eval + 서빙 운영 | 프롬프트(1) → RAG(2) → LoRA/SFT(3) → DPO+eval 하네스(4) → 다중모델+서빙운영(5) |
| **규제위험** | 낮을수록 좋음 | 규제 표면 없음 | 라이선스 직역 침해 / 인허가 / 결제 차단 | EU AI Act Art.50, SB 243, HIPAA, 무자격 법률·의료행위, 카드사 정책 |
| **수익모델** | 높을수록 좋음 | 일회성, 이탈 쉬움 | 초기 커스터마이징비 + 구독 + 전환비용 | 기획서의 5종(커스터마이징비/구독/API 종량/private hosting/어댑터 라이선스) 중 몇 개가 맞물리는가 |

**Fit = 시장성 + 수익모델 − 기술난이도 − 규제위험** (범위 −8 ~ +8). 정렬 보조용이지 의사결정 규칙이 아닙니다.

### 3-1. 규제 축을 고정하는 2026년 현재 사실

이 축만은 판단이 아니라 사실이라 따로 적습니다.

- **EU AI Act Art.50 투명성 의무는 2026-08-02부터 실제 발효**했고 연기되지 않았습니다. 그 이전 출시 시스템은 **2026-12-02**까지 유예. AI Office의 GPAI 집행 권한(과징금·리콜)도 같은 날 발효.
- **고위험(Annex III) 의무는 2027-12-02로 연기**됐습니다 — Digital Omnibus(Regulation (EU) 2026/1744, 2026-07-27 발효). 규제 산업 니치의 시계가 1년 이상 뒤로 밀렸다는 뜻입니다.
- **California SB 243(컴패니언 챗봇)은 2026-01-01 발효** — 이미 시행 중입니다. AI임을 고지, 미성년자에게 **3시간마다 휴식 알림**, 자해·자살 관련 콘텐츠 차단 프로토콜, 2027년부터 주 보건국 보고, 그리고 **사적 소권(private right of action)**. 마지막 항목이 1인 사업자에게 특히 무겁습니다 — 규제 당국이 아니라 **개인이 직접 소송**할 수 있습니다.
- **라이선스**: Qwen3 이후 Apache 2.0, DeepSeek 상용 친화(단 **학습 데이터 출처는 분쟁 중** — 규제 산업이면 법률 검토 필요), Llama는 MAU 7억 임계.

## 5. 상위권에서 반복되는 패턴 — 점수보다 이게 결론입니다

Fit 상위 5개를 나란히 놓으면 **점수를 매기기 전에는 안 보이던 공통점**이 나옵니다.

**① 상위권은 전부 "출력 품질을 채점할 수 있는" 제품입니다.**
설정 일관성(#3)은 모순이 있냐 없냐, 비식별화(#14)는 가려졌냐 아니냐, 매뉴얼 QA(#12)는 매뉴얼에 그 문장이 있냐 없냐. 전부 **결정론적 정답이 있습니다.**
반대로 하위권(#1 GM 엔진, #2 컴패니언, #11 VTuber)은 전부 **"좋은 서사인가"를 물어야 하는 제품**입니다.

이게 우연이 아닌 이유: 08-30 문서 §5-5의 약점 3번 — **judge 노이즈 바닥 ~1점**. 품질을 못 재면 **LoRA가 base보다 나은지 증명할 수 없고**, 증명 못 하면 커스터마이징 비용을 청구할 근거가 없습니다. 기획서의 밸류체인에서 "개인 Customization"이 값을 만드는 유일한 방법은 **그 커스터마이징이 효과가 있음을 보이는 것**인데, 주관적 품질 도메인에서는 그걸 보이는 도구 자체가 없습니다.

> **재정식화한 최종 연구 질문:**
> "1인 개발자가 롱테일 니치를 어떻게 발견/특화/수익화하는가"가 아니라 —
> **"어떤 니치가 *특화의 효과를 증명 가능하게* 만드는가."** 증명 가능성이 시장 크기보다 먼저 오는 필터입니다.

**② 규제위험 5점 칸은 전부 "빅테크가 안 오는 이유"와 같은 이유로 1인도 못 갑니다.**
#2 컴패니언, #4 성인, #6 의료. 기획서는 "대기업에게 정책·브랜드 리스크가 있지만 개인에게는 수익성 있는 시장"을 노리자고 하지만 — **컴플라이언스 비용은 매출에 비례하지 않고 고정비**입니다. SB 243의 3시간 알림·자해 프로토콜·주 보건국 보고를 구현하는 비용은 사용자 100명이든 10만 명이든 거의 같고, **사적 소권은 1인 사업자에게 더 치명적**입니다. 이 축에서 빅테크의 회피는 기회가 아니라 **선행 지표**입니다.

**예외는 "정책 리스크"가 아니라 "규모 리스크"로 회피하는 칸입니다** — #16 레거시 마이그레이션, #12 매뉴얼 QA, #18 한문. 빅테크가 안 오는 이유가 *위험해서*가 아니라 *작아서*인 칸. **기획서가 겨냥해야 할 것은 "귀찮거나 작은" 쪽이지 "정책·브랜드 리스크" 쪽이 아닙니다.**

**③ GPU 경제성은 상위권 선정에 아무 영향을 못 줬습니다.**
§2에서 인프라 손익분기가 가동률 8%로 나왔기 때문에, 20개 니치 어디서도 GPU 비용이 결정 변수가 아니었습니다. 기획서 밸류체인의 "Local/GPU Serving" 층은 **해결된 문제**입니다. 남은 건 전부 그 위층(제품/유통)과 아래층(품질 증명)입니다.

## 6. 그래서 MythOS는 이 판에서 무엇인가

**니치로서의 #1(GM 엔진)은 Fit −1로 표의 하위권입니다.** 신규 진입 대상으로는 최악에 가깝습니다: 기술난이도 5, 품질이 주관적이라 증명 불가.

**그런데 자산으로서의 MythOS는 표의 어느 행도 아닙니다.** 08-30 문서 §5-2가 이미 짚은 대로, 이 리포지토리가 가진 희소 자산은 게임이 아니라 **품질 축을 가진 워크로드**입니다 — 해시 고정 held-out 뱅크, development/promotion 분리, 루브릭 SHA-256 provenance, 그리고 **자기 judge의 노이즈 바닥을 실제로 잰 기록**.

§5의 패턴 ①과 합치면 이렇게 됩니다:

> 상위권 니치가 상위권인 이유는 **품질 측정 문제를 회피**하기 때문이고,
> MythOS가 희소한 이유는 그 문제를 **회피하지 않고 정면으로 재 본** 거의 유일한 사례이기 때문입니다.

이 둘은 모순이 아니라 역할 분담입니다. **수익화는 측정 문제가 없는 니치에서, 연구·평판 자산은 측정 문제를 정면으로 다룬 MythOS에서** — 그리고 후자가 전자의 신뢰도가 됩니다("이 사람은 자기 judge 노이즈를 재는 사람이다"는 #5 법무·#6 의료 같은 고신뢰 B2B 칸에서 실제 영업 자산입니다).

## 7. 다음 단계 (순서대로)

1. **`usage.py` 배포 + 1주 수집** — 08-30 문서의 단계 0과 동일. §2의 $0.171이 추정에서 측정으로 바뀌고, `cost_per_loop_usd ~$1.0`의 6배 과대를 확정 또는 반증합니다. **이 문서에서 가장 값싸고 가장 확실한 다음 행동.**
2. **루브릭 결정 가능성 (오너 미결)** — §5의 결론에 따라 이건 이제 제품 블로커·연구 블로커에 더해 **사업 모델 블로커**입니다. 세 선택지(N회 중앙값 / judge 엔진 고정 / 숫자 게이트 폐기)는 08-30 문서 그대로.
3. **상위권 2~3개를 니치 스카우팅으로 검증** — 표의 점수는 판단이므로, #3/#12/#9에 대해 **실제 잠재 고객 5명과 대화**해서 시장성 점수를 판단에서 관찰로 바꿉니다. 코드 이전에 할 일.
4. **multi-LoRA TTFT 실측** — §1-1의 10배 TTFT 함정을 자기 컨텍스트 길이 분포에서 확인. `labs/wsl2-vllm-baseline/` + 골든 뱅크 리플레이(08-30 §5-4의 `mythos` 시나리오)로 가능. 이건 사업 검증이자 연구 산출물.
5. **§8의 미검증 처리량 가정 확정** — 4번과 같은 실험에서 같이 나옵니다.

**하지 않을 것**: 지금 니치를 하나 골라 코딩 시작. 3번이 먼저입니다. 이 표의 시장성 열은 전부 판단이고, 판단으로 12개월을 쓰는 것이 이 기획의 가장 큰 실패 모드입니다.

## 8. 확인 필요 / 미검증

- **§2-2의 처리량 가정(prefill 10,000 tok/s, decode 1,000 tok/s)** — 이 문서에서 가장 약한 숫자입니다. 손익분기 8.2%가 여기 정비례합니다. 실제가 1/3이면 임계는 25%로 올라갑니다. `labs/`에서 측정 가능.
- **단가 전부** — 2차 출처(벤더 블로그·비교 사이트). 공식 가격표 원문 미대조. Gemini Flash 입력 단가는 **90일 만에 50% 하락** 이력이 있어 유효기간이 짧습니다.
- **§4의 시장성 열 전체** — 관찰이 아니라 판단. 고객 대화 전에는 근거 없음(§7-3).
- **$41K MRR 사례(#17)** — 콘텐츠 마케팅성 2차 출처. 검증 안 됨. 유형의 존재 증거로만 쓰고 수치는 인용하지 말 것.
- **SB 243의 역외 적용 범위** — 캘리포니아 거주자 대상 서비스에 어디까지 미치는지 법률 검토 미수행. #2/#4 판단이 여기 걸림.
- **DeepSeek 학습 데이터 출처 분쟁** — 규제 산업(#5/#6) 채택 시 별도 법률 검토 필요.
- **08-30 문서의 p151 인용** — 이 문서 §2-4에서 정정. 원문 재확인은 여전히 `[manual]`.
